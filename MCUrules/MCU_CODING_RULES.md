# Правила разработки программного обеспечения микроконтроллера

## 1. Назначение и приоритеты

Код создаётся только для данного проекта. Переносимость на другие проекты и платформы не является приоритетом.

Основные требования:

1. Код должен быть простым, понятным и удобным для чтения человеком.
2. Код необходимо оптимизировать по скорости выполнения, если это не делает его неоправданно сложным.
3. Частоту микроконтроллера и конфигурацию тактирования необходимо брать из файла `.ioc`.
4. Для работы с периферией необходимо использовать STM32 HAL.
5. Необходимо соблюдать стиль кода, принятый в STM32CubeIDE и генерируемом STM32CubeMX коде.
6. Использовать соглашения стандарта C99.

## 2. Организация проекта

### 2.1. Инициализация оборудования

Вся прикладная инициализация периферии должна выполняться в файлах:

- `HardwareInit.c`;
- `HardwareInit.h`.

Файл `main.c` должен оставаться минималистичным. В нём допускаются только запуск системы, вызов общей инициализации и основной цикл верхнего уровня.

### 2.2. Разделение программных модулей

Необходимо соблюдать следующие правила:

1. Один драйвер — одна пара файлов `.c/.h`.
2. Одна периферийная подсистема — одна пара файлов `.c/.h`.
3. Одна логически связанная группа вычислений — одна пара файлов `.c/.h`.
4. Все функции, относящиеся к одному модулю, должны находиться в его собственных `.c/.h`.
5. Каждый модуль должен быть снабжён комментариями, поясняющими его назначение и правила использования.
6. В заголовочном файле сразу после заголовка файла должен находиться пример использования модуля.

Каждая самостоятельная подсистема должна быть строго выделена в собственную пару файлов `имя.c/.h`. Нельзя объединять в одном модуле логически независимые подсистемы только из-за того, что они используют общую периферию или вызываются из одного места.

Например, управление лазером размещается в `laser.c/.h`, а связанные с ним расчёты пыли — в отдельном модуле `dust_calc.c/.h`.

## 3. Передача и хранение данных

1. Данные инициализации должны храниться и передаваться в структурах.
2. Составные входные, рабочие и возвращаемые данные должны храниться и передаваться в структурах.
3. Простые скалярные параметры и результаты разрешены, если они делают интерфейс функции проще и понятнее.
4. Не следует создавать структуру только ради передачи одного простого значения.
5. Функции должны возвращать понятный статус выполнения. Для набора статусов следует использовать именованный тип `enum`.
6. Если функции необходимо вернуть одновременно статус и данные, статус возвращается через `enum`, а данные записываются в переданную структуру либо в простой выходной параметр для одного скалярного значения.
7. Переменные, используемые одновременно в основном цикле и обработчиках прерываний, необходимо объявлять и применять с учётом конкурентного доступа.
8. Для защиты совместно используемых данных необходимо использовать подходящий механизм: критическую секцию, временное отключение прерываний либо другой явно обоснованный способ.
9. Критическая секция должна быть минимальной по длительности.

## 4. Динамическая память

1. Следует избегать динамического выделения памяти.
2. Перед применением динамической памяти необходимо явно запросить разрешение пользователя.
3. В запросе необходимо объяснить, почему статическое размещение недостаточно, указать ожидаемый объём памяти и описать обработку ошибки выделения.
4. Без полученного разрешения использовать `malloc`, `calloc`, `realloc`, `free` и аналогичные механизмы запрещено.

## 5. Работа с HAL и обработка ошибок

1. Все функции, взаимодействующие с HAL, должны проверять возвращаемые значения HAL-функций.
2. Ошибки нельзя игнорировать или скрывать.
3. Функция должна корректно завершать операцию и возвращать вызывающему коду понятный статус.
4. Статусы модуля должны различать как минимум успешное выполнение, неверные аргументы, ошибку HAL, занятость и тайм-аут, если эти состояния применимы.
5. Если HAL-функция может частично изменить состояние оборудования до возникновения ошибки, модуль должен привести оборудование в безопасное или документированное состояние.

## 6. Требования к заголовочным файлам

Каждый заголовочный файл `.h` должен:

1. Использовать include guard.
2. Содержать `#include "main.h"`.
3. Содержать номер версии файла.
4. Содержать все публичные структуры, перечисления, константы и объявления функций модуля.
5. Содержать пример использования сразу после заголовка файла.
6. Содержать рядом с ключевыми `#define` пример расчёта значения.

Формат версии:

```c
#define DRIVER_VERSION    yyxxx
```

Где:

- `yy` — двухсимвольная аббревиатура имени файла;
- `xxx` — порядковая версия драйвера или модуля.

Пример для первой версии `laser.h`:

```c
#define LASER_VERSION    LS001
```

Аббревиатура должна быть уникальной и сохраняться во всех следующих версиях файла.

## 7. Константы и драйверы микросхем

1. Все необходимые константы модуля должны быть оформлены через `#define` в соответствующем заголовочном файле.
2. Не допускаются необъяснённые числовые литералы в исполняемом коде.
3. Для ключевых констант необходимо привести рядом пример расчёта.
4. При создании драйвера микросхемы константы из документации, используемые драйвером, должны быть перенесены в именованные `#define`.
5. К таким константам относятся адреса, регистры, маски битов, команды, коэффициенты пересчёта, ограничения, тайм-ауты и значения по умолчанию.
6. Названия констант должны однозначно указывать на модуль и назначение значения.

## 8. Комментарии и документация

1. Все комментарии должны быть написаны на русском языке в кодировке UTF-8.
2. Если существующие комментарии используют другую кодировку или язык, при изменении соответствующего участка их необходимо исправить.
3. В коде и примерах запрещено использовать последовательности начала и завершения блочного комментария.
4. Все комментарии должны начинаться с `//` в начале строки.
5. Для Doxygen необходимо использовать строчные комментарии `///`.
6. Каждая функция должна иметь Doxygen-комментарий с полем `@brief`.
7. Для параметров, результата и возможных статусов следует использовать `@param`, `@return` и другие подходящие Doxygen-поля.

Пример допустимого оформления:

```c
/// @brief Запускает измерение с заданными параметрами.
/// @param context Указатель на структуру состояния модуля.
/// @param request Указатель на структуру параметров измерения.
/// @return Статус выполнения операции.
MeasurementStatus Measurement_Start(MeasurementContext *context,
                                    const MeasurementRequest *request);
```

## 9. Поддержка спецификаций

Изменение поведения продукта и обновление спецификации должны выполняться в одном рабочем цикле.

После каждого изменения кода, которое влияет на поведение во время выполнения, форму модели данных, валидацию, экспорт, семантику пользовательского интерфейса или доступный набор параметров, необходимо:

1. Немедленно определить затронутые файлы спецификаций.
2. Обновить эти файлы в рамках той же задачи.
3. Не переносить обновление спецификации на последующую необязательную задачу.
4. Не оставлять новое поведение описанным только в коде или истории обсуждения.

Перед изменением логики действий, валидации, поведения экспорта или семантики панелей необходимо заново прочитать соответствующие спецификации.

### Выбор файла спецификации

Файл спецификации выбирается по имени и назначению изменяемой подсистемы. Обычно модулю `имя.c/.h` соответствует файл `Specification/имя.md`. Если отдельного файла для подсистемы нет, изменение необходимо описать в наиболее близкой по назначению спецификации либо в `Specification/misc.md`.

Например, изменения управления лазером, а также связанного с ним поведения DMA, DAC, ADC или TIM необходимо сверять и документировать в `Specification/laser.md`.

Если изменение затрагивает несколько подсистем, необходимо прочитать и обновить все соответствующие файлы спецификаций.

## 10. Порядок уточнения требований

Если для выполнения задачи требуются уточнения:

1. Задавать вопросы по одному.
2. Для каждого вопроса предлагать несколько вариантов ответа.
3. Всегда указывать рекомендуемый вариант по умолчанию.
4. Не начинать изменение, зависящее от ответа, если неверное предположение может существенно изменить результат.

## 11. Проверка перед завершением задачи

Перед завершением изменения необходимо проверить:

- частота и тактирование соответствуют `.ioc`;
- `main.c` остался минималистичным;
- инициализация периферии размещена в `HardwareInit.c/.h`;
- соблюдено разделение модулей по файлам;
- интерфейсы данных соответствуют правилам структур;
- динамическая память не применена без разрешения;
- результаты HAL-функций проверяются;
- совместно используемые с прерываниями данные защищены;
- заголовочные файлы содержат include guard, `main.h`, версию и необходимые `#define`;
- каждая функция имеет русскоязычный Doxygen-комментарий с `@brief`;
- комментарии имеют кодировку UTF-8 и используют только строчный формат;
- затронутые спецификации прочитаны до изменения поведения и обновлены после него;
- новое поведение не осталось описанным только в коде или обсуждении.
